---------------------------------------------------------------------
5. 実装上の必須条件
---------------------------------------------------------------------
- CDS にデータモデルと service 定義を作成する。
- 標準 CRUD で実現できる部分は標準機能を利用し、不要な @On READ は作らない。
- 業務チェックは UI だけでなく CAP Java の @Before または action 内でも実施する。
- 複数更新が必要な業務処理は OData action と Java の @On で実装する。
- 認可は CDS の @restrict / @requires を優先して定義する。
- Fiori elements で実現できる画面制御は CDS annotation を優先する。
- UI5 extension は、標準 annotation で実現できない場合だけ追加する。
- 接続先 URL、ユーザー、パスワード、トークンをソースコードやログに書かない。
- 外部システム連携は Destination 等の安全な設定を利用する。
- エラーメッセージは利用者が分かる日本語で返す。

---------------------------------------------------------------------
6. AI に提出してほしい成果物
---------------------------------------------------------------------
1. 実装前の設計概要
   - エンティティ、親子関係、サービス、画面、認可の一覧
   - Backend と Frontend の責務分担

2. 変更対象ファイル一覧
   - 新規／修正の CDS、Java、annotation、UI5 extension、設定、テスト

3. 実装
   - 既存コード・既存の命名規則・既存のパッケージ構成に合わせる
   - 不要な依存関係、ダミー値、認証情報を追加しない

4. テスト
   - 正常系、入力エラー、認可エラー、action 実行、外部連携失敗時を確認する
   - 実行したコマンドと結果を報告する

5. 最終報告
   - 変更内容
   - 検証結果
   - 未実装／前提条件／利用者が設定する値

---------------------------------------------------------------------
7. 受入条件
---------------------------------------------------------------------
- 指定ロールで一覧・詳細画面を利用できる。
- 必須入力・業務チェックで不正データを保存できない。
- 親子データの登録・変更・削除が正しく反映される。
- 親子の合計・状態などの整合性が保たれる。
- 指定 action が実行条件を満たすときだけ実行できる。
- 外部連携が必要な場合、成功・失敗時ともに利用者向けメッセージが表示される。
- 既存機能・既存テストを不必要に変更しない。

■ 記入例：受注管理アプリ
======================================================================
アプリ名     : 受注管理
業務目的     : 受注ヘッダと明細を登録し、承認者が承認する。
親子関係     : Orders 1 : n OrderItems（composition）
チェック     : 明細は 1 件以上、数量は 1 以上、親の合計額は明細合計と一致する。
action        : approveOrder。SUBMITTED の受注だけ承認可能。
認可          : Viewer は閲覧のみ、Editor は登録・変更、Approver は承認可能。
画面          : List Report + Object Page。登録日の降順で表示する。
画面制御      : APPROVED になった受注は Header／Item とも編集不可にする。

この例をそのまま実装せず、上記「業務の概要」から「受入条件」を案件に合わせて
具体化してから AI に依頼する。
